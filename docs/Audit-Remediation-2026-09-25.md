## Rollout

1. Take and independently verify an encrypted backup before production migration. Apply migrations `0052` through `0060` with the existing migration runner: policy review, MFA, scheduled jobs, settlement reconciliation, privacy requests, language preferences and access exports/correction proposals, settlement payment records and signed-contract compensation proposals. Existing settlement cases without a reviewed reconciliation snapshot must be re-reviewed; approved legacy cases require cancellation and a new case. No production migration was run here.
2. Set `MFA_ENCRYPTION_KEY` to a securely generated independent 32-byte key encoded as 64 hex characters. Back it up separately from the database. Do not replace this key casually: existing authenticator seeds require it. Stage enrollment first, then set `MFA_ENFORCE_PRIVILEGED=true`. This requires admin, super-admin, HR, HR-director, HR-manager, payroll and finance roles to enroll before business API access.
3. Enrollment/replacement revokes every existing session and presents fresh recovery codes once. Save them before leaving the page. A lost device requires password plus unused recovery codes to sign in and verify replacement. There is no public administrator bypass for a user who has lost every factor; establish an independently approved recovery process before wide rollout. MFA failure counters are database-backed; HTTP credential throttling additionally applies.
4. Configure `CLAMD_HOST` and `CLAMD_PORT` only on a trusted private network. The ClamAV TCP protocol is unauthenticated and must not be exposed publicly. Keep signatures updated and configure `StreamMaxLength` at least 40 MB and `AlertExceedsMax yes`, with appropriate parser/archive limits. Set `FILE_SCAN_REQUIRED=true` after provisioning. New uploads stay in request memory until clean; scanning failure creates no downloadable object. Historical files require separate screening.
5. Provision an external scheduler to POST `/internal/scheduled-jobs` over HTTPS every minute, with `Authorization: Bearer <SCHEDULER_SECRET>` (at least 32 random characters). Keep the secret in the scheduler's secret store, never the URL or logs. Configure a request timeout allowing job completion. After verifying invocations, set `SCHEDULER_MODE=external`; otherwise the compatible in-process loop remains. Inspect Services & recovery for job health. Failed work becomes eligible after one minute; crash leases expire after 30 minutes. Existing report schedules retain their own attempt/deduplication rules. Do not count host cold-start latency as an exact-time guarantee.
6. Set `APP_DATA_MODE=demo` for demonstration workspaces. Set `operational` only after verifying sample-data separation. In production, an unset mode blocks bank export and payment recording. The setting does not classify or remove existing records. Set `PRIVACY_RESPONSE_DAYS` to the approved operational target (1–90 days, default 30); this is not a jurisdictional legal deadline. Set `APP_RELEASE` to the deployed commit if the host does not supply `RENDER_GIT_COMMIT`.
7. Enable operational services and complete each external acceptance gate in the table. Keep any failed gate open rather than treating a configuration value as proof of delivery.

An external worker can invoke `node scripts/invoke-scheduled-jobs.mjs` with `APP_URL` and `SCHEDULER_SECRET` in its secret environment. The command has a 120-second deadline, refuses credential-bearing or redirected destinations, and exits nonzero for unsuccessful/incomplete responses. Configure monitoring on that exit status and verify the application job history after a timeout. This command does not itself install a recurring schedule.

Privacy administrators must verify identity, review the requested scope and supplemental disclosures, and inspect the saved core export before independent release. The released file remains the prepared snapshot even if source records later change. Generated exports contain sensitive personal data and require the same database access/backup protection and an approved retention/disposal policy. No automatic deletion policy has been invented. Correction fulfilment applies the prepared allowlisted values and closes the request in one transaction; stale profiles require a fresh proposal.

## Settlement payment follow-up

Migration `0059_settlement_payments.sql` adds versioned payment reviews and unique payroll allocations. Administrators can propose evidence of an external payment only for a completed case with a positive net settlement. The recorded amount must equal the immutable reviewed net. Linked approved payroll must match the reviewed outstanding salary, and leaving-year leave debits must match the reviewed encashed days. Previously exported WPS payroll is blocked pending bank reconciliation; this workflow does not resolve bank submissions or transfer money. A different active administrator, also the designated pay approver for every linked payroll, must confirm the evidence. Proposals with different designated approvers, a self-designated approver or a non-administrator approver are blocked up front; the underlying payroll needs an eligible common administrator approver before using this cross-module workflow.

Pending/recorded allocations prevent separate payroll mutation, payment recording and WPS export. Rejection releases allocations. Changed source balances reject confirmation and require a fresh proposal. Confirmation applies payroll/time locks, leave debits, payment status and audit history atomically. Repeated confirmation cannot debit or pay again. Database triggers also prohibit editing/deleting recorded payments and altering evidence during the review decision. Historical proposals and rejection reasons remain in audit history and the latest 100 events are shown. Only leaving-year leave balances are allocatable; prior-year carryover must be reconciled before proposal to avoid paying the same carried entitlement twice. Nonpositive net settlements and partial payments are not supported by this workflow.

## Signed contract compensation follow-up

Migration `0060_contract_compensation.sql` adds immutable, versioned proposal decisions. In Employee Database → Salary & benefits, eligible scoped HR users can select a signed contract, compare its English and Arabic terms, prepare the complete salary/benefit breakdown and submit it. A different eligible HR reviewer must approve the proposal before it creates a new compensation revision. The employee/contract recipient cannot prepare or review their own mapping. Existing compensation and payroll remain unchanged while a proposal is pending.

The source contract fingerprint, employee, proposed definition, date and expected compensation version are pinned. Unsigned/foreign contracts, out-of-period effective dates, changed compensation, conflicting retry payloads and duplicate application are rejected. Rejection preserves the proposal and permits a fresh one. Successful application creates one immutable package and its audit record atomically. The package then uses the existing separately confirmed payroll-rule mapping; publication preserves historical payroll amounts and retains applicable deductions. This does not parse legal prose automatically, sign a contract, amend employment dates, certify legal applicability, or integrate a general ledger.

Focused contract/separation and deployment-migration checks passed **20 tests**, including audit-failure rollback and payroll publication from the approved package. The isolated browser exercised submission as one account and approval as another: package version 1 remained current while pending, then version 2 became current with version 1 retained. No self-approval action was shown, Arabic mapping status was verified, mobile control bounds fitted the viewport, and no console errors were returned. Production UI and server bundles passed.
